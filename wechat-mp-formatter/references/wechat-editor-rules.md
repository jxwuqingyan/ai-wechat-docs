# 微信公众号编辑器兼容规则

公众号后台（mp.weixin.qq.com）的富文本编辑器不是一个「HTML 导入工具」。粘贴进去的 HTML 会经过
**结构清洗 → 属性过滤 → 移动端再渲染** 三轮处理，最终只保留一部分标签和一部分内联样式。
下面这份表是排版时必须遵守的边界。

## 1. 标签支持情况

| 类别 | 标签 | 结论 |
| --- | --- | --- |
| 结构块 | `section`、`p`、`div`（常被转成 section） | ✅ 保留，是正文的主力容器 |
| 标题 | `h1` ~ `h6` | ⚠️ 基本保留；追求极致稳定可用 `--flat-tags` 全部降级成 `<p>` |
| 强调 | `strong`/`b`、`em`/`i`、`u`、`del`/`s` | ✅ 保留，且有浏览器默认样式（不必自己写 style） |
| 引用 | `blockquote` | ✅ 保留，可自定义左边线与背景 |
| 列表 | ❌ 不用 `ul`、`ol`、`li` | 序号/圆点靠 CSS 的 `list-style`，清洗后整篇有序项会全变 `1.`；本项目把序号写成文本，见第 5 节 |
| 表格 | `table`、`thead`、`tbody`、`tr`、`th`、`td` | ✅ 保留，但**必须**自己写 border，默认无边框 |
| 代码 | `pre`、`code` | ⚠️ 标签能被保留，但 `pre` 会触发后台「内容结构检测」警告（见第 4 节）；本项目改用 section + span 方案，不输出这两个标签 |
| 图片 | `img` | ✅ 保留，但 src 必须是已上传的素材地址 |
| 行内容器 | `span` | ✅ 保留（配合 inline style 是万金油） |
| 分隔 | `hr` | ⚠️ 基本可用；用带背景的 `<span>` 做装饰线更稳 |
| 禁止项 | `script`、`style`、`link`、`iframe`、`form`、`input`、`video`、`svg` | ❌ 剥离或屏蔽 |

## 2. 属性过滤

- `class`、`id`、`name`、`data-*` → **清理**
- `style` → 保留，但做属性名/值过滤
- `onclick` 等事件属性 → 清理
- `href` → 保留，但公众号正文中的外部链接点击受限（见第 6 节）

## 3. 内联 CSS 属性

**可用（放心用）**：`color`、`font-size`（建议 px）、`font-weight`、`font-family`、
`line-height`、`letter-spacing`、`text-align`、`text-indent`、`text-decoration`、
`margin`、`padding`、`border`（含 `border-radius`）、`background-color`、
`background-image`（含 `linear-gradient`）、`background-size`、`background-repeat`、
`box-shadow`、`opacity`、`white-space`、`overflow-x`、`word-break`、`vertical-align`、
`display`（block / inline-block / inline）、`min-height`、`width` / `max-width`（百分比或 px）。

**明确不可用**：

| 属性 | 后果 |
| --- | --- |
| `position: fixed / absolute / sticky` | 被清掉，元素塌回文档流，版面错位 |
| `transform`、`animation`、`transition` | 不支持，静态部局不要依赖 |
| `float` | 不稳定，用不了布局 |
| `display: flex / grid` | 会被降级为 block，布局散架 |
| `:hover` 等伪类 | 无意义（移动端无指针） |
| CSS 变量、`calc()` 复杂表达式 | 支持不稳定 |

## 4. 代码块保真的关键：分行必须交给“结构化标签”

代码块踩过三个坑，按时间顺序记下来，避免再走回头路：

**坑一：`<pre><code>`。**
后台的「内容结构检测」会弹窗提示「当前使用了 pre 标签（预格式化文本），内容不会自动换行，
移动端可能出现水平溢出」；而且 `<pre>` 的换行能力本来就依赖 `white-space`，
这个属性一旦被清洗，整个代码块会挤成一行。

**坑二：`<span style="display:block">`（看起来对，实际上是错的）。**
改成「每行一个 display:block 的 span」后，在本地预览、在浏览器里都完全正常，
但**粘到公众号后所有代码行会无缝挤成一行**，例如：

```
$ cat >> /etc/sysctl.conf << EOFvm.swappiness = 1vm.dirty_background_ratio = 5
```

原因是微信在保存/预览时会重新解析正文并清洗内联样式。实测下来的规律是：

| 观察到的现象 | 说明 |
| --- | --- |
| 容器 `<section>` 上的 `background-color` / `border-radius` 都活着 | 容器的样式基本保留 |
| 装饰用的 `<span style="display:inline-block;width:9px;height:9px">` 圆点也活着 | 不是“无差别清洗 span 样式” |
| 但 `<span style="display:block">` 的 `display` 没了 | 一旦退回行内元素，相邻行之间**连一个换行符都没有**，于是整块挤成一行 |

关键在于：**那几行代码之间没有任何真正的换行标签**，分行 100% 依赖 `display`。
一个属性被洗掉，就全军覆没。

**现在的做法（坑三已避开）：分行用 `<section>`，块级来自标签语义，不依赖任何 CSS。**

| 目标 | 做法 | 为什么可靠 |
| --- | --- | --- |
| 分行 | 每行一个 `<section style="margin:0;padding:0">` | 块级是标签自带的，**style 被整条洗掉也不会串行** |
| 空行 | `<section ...>&nbsp;</section>` | `&nbsp;` 撑出正常行高，不靠 `min-height` |
| 保缩进 | 空格写成 `&nbsp;` | HTML 实体不会被空白折叠吃掉 |
| 上色 | 每个 token 一个 `<span style="color:#xxx">` | class 会被清理，内联色值不会被清（退化时只是没颜色，不会乱版） |

下面这条是硬规则：**正文里承载“结构含义”（分行、分栏、占位）的东西，只能用
`<section>` / `<p>` / `<br>` 这类自带块级语义的标签，不能靠 `display` 撑。**
样式只负责好看，不能负责结构。

再补三条实践结论：

- 长行默认 `word-break:break-all`，在容器宽度内折行 → 移动端不会水平溢出。
  外层不再写 `white-space`：空格已经全部是 `&nbsp;`，不需要它参与，
  少一个属性就少一处被清洗的不确定性（实测 `break-all` 足以折行，无横向溢出）。
- 若更在意代码「原样单行」（长命令、表格化输出），用 `--code-mode scroll`：
  外层改用 `white-space:pre; overflow-x:auto`，超宽部分靠横向滚动查看。
  代价是部分机型看不到右半部分，且结构检测仍可能提示溢出风险。
- **不要在每行 section 里再补 `<br>`**：块级已经换行，`<br>` 会再叠一行空行。

`check_html.py` 会主动检查这几件事：

- 产物里出现 `<pre>` 标签 → 警告；
- 出现 `white-space:pre`（非 `pre-wrap`）→ 提示溢出风险；
- **代码块里出现 `<span style="display:block">` → 直接报错**（就是上面踩过的坑，
  属于「粘过去一定乱」的级别，自检面板会标成必须修复）。

### 验证代码块没被改坏的方法

代码块的缩进和空行最容易在改动中悄悄丢失，肉眼很难看出来。可靠的验证是
**把生成的 HTML 逐行还原成纯文本，与原始文档逐行比对**：

- 每行是一个 `<section style="margin:0;padding:0">`，配对取内容后剥标签、还原实体；
- 比对前把 `&nbsp;` 还原成空格、`Tab` 展开成 4 空格（这两者是**有意的**变换）；
- 空行会被写成 `&nbsp;`，比对时 `rstrip()` 即可对齐；
- **不要**用「先剥行号」的正则去 `lstrip` 掉整段前导空白 —— 那正是代码缩进。

还有一个更狠、也更值得做的一步：**模拟微信清洗后重新渲染**。
把产物里所有 `<span style="...">` 的 style 抹掉再截图，如果代码行依然各占一行，
说明分行没有依赖样式；如果挤成一行，就说明还没修干净。

`scripts/` 下没有内置这两个验证脚本，改动代码块逻辑后按上面的思路临时写一段即可。

## 5. 列表编号保真的关键：序号必须是文本

列表的坑和代码块是同一个坑的两副面孔：**把「结构含义」交给了 CSS**。

`<ol>` 的序号不是内容，是 CSS（`list-style`）画出来的。微信重排正文时会洗掉
`list-style`，于是：

- 轻则整篇有序项全部显示成 `1.`（每个 `<li>` 都按「第一项」画）；
- 重则编号整体消失，只剩裸文本。

更常见、也更隐蔽的一种触发方式是**列表被正文/代码块打断**。写教程时最自然的写法就是
「步骤 1 → 一段说明 → 一段命令 → 步骤 2」，但解析器会把它切成两个列表，
输出成两个 `<ol>`，**每个 `<ol>` 都从 1 重新开始**：

```
1. 确认从库未初始化数据目录      ← 第 1 个 <ol>，从 1 开始
   （说明段落 + 代码块夹在中间）
1. 使用 pg_basebackup 创建从库基础备份   ← 第 2 个 <ol>，又是从 1 开始
```

**现在的做法：不用 `ol`/`ul`/`li`，序号直接写成文本。**

| 目标 | 做法 | 为什么可靠 |
| --- | --- | --- |
| 每一项 | 一个 `<section style="margin:6px 0;padding-left:1.9em;text-indent:-1.9em">` | 项与项之间是块级标签，天然分行 |
| 序号 | 文本 `1.` / `2.` 或圆点 `•` / `◦` / `▪`，包在 `<span style="display:inline-block;width:1.9em">` 里 | 序号是内容，style 全被洗掉也照样显示 |
| 悬挂缩进 | `padding-left` + `text-indent:-1.9em` | 换行后的第二行与首行正文对齐；即使这两个属性被洗掉，也只是「不缩进」，**不会错行** |
| 续号 | 渲染器按层计数：同一标题下被正文/代码块打断的列表接着数 | 与作者的实际意图一致 |
| 归零 | 遇到标题（`h1`~`h6`）、分隔线，或解析器标了 `restart`（Word 里换了 `numId`） | 新的一节就是新的一轮编号 |

序号层级沿用原来的语义：一层 `1.` → 二层 `a.` → 三层 `i.`；无序一层 `•` → 二层 `◦` → 三层 `▪`。

两条容易踩的细节：

- **`text-indent` 是继承属性**。列表项里的代码块、后续段落都是块级子元素，
  它们的首行会被外层那个 `text-indent:-1.9em` 往左拽出去。所以列表项里的
  非首行内容统一包一层 `<section style="text-indent:0">`。
- **列表项的首个段落要内联进 marker 那一行**，不能再包 `<p>`；
  否则序号会独占一行、正文掉到下一行（`<li>` 有浏览器的特殊 marker 规则，`<section>` 没有）。

`check_html.py` 会主动拦这两件事：

- 产物里出现 `<ol>` / `<ul>` / `<li>` → **直接报错**（序号依赖 `list-style`，
  属于「粘过去编号就废」的级别）；
- 分类混写不会再发生：Markdown 里紧跟有序列表的无序列表、Word 里换了枚举定义的无序项，
  都会被识别成另一串列表，而不会被吞进编号里（圆点变数字就是这么来的）。

### 验证列表没被改坏的方法

- **模拟微信清洗**：把产物里所有 `style` 属性（不止 span 上的）整条抹掉再渲染，
  编号仍然应该是 `1. 2. 3.` 而不是四行 `1.`。这是最接近真实后台的验证。
- **按键值序列断言**：把所有 marker 的文本按顺序抓出来，
  和预期的 `1. 2. 3. 4. / 1. 2. / • • ◦ ◦ / 1.` 比对，比肉眼看截图可靠。

## 6. 链接与图片

- **链接**：公众号正文按规定不能放任意外部链接（只有已认证主体可用的白名单、公众号文章、
  小程序、视频号等有限形态）。`<a href>` 保留下来通常也是不可点/提示受限。
  因此处理策略：
  - `--link-mode keep`（默认）：保留 `<a>`，视觉上有下划线即可
  - `--link-mode text`：**推荐给教程类文章**，把地址明文写在括号里，读者可以复制
  - `--link-mode strip`：只留文本
- **图片**：粘贴时微信会尝试转存部分外链图，但本地路径 / base64 / 相对路径**一定失败**。
  正确流程是：先在公众号后台「图片」里上传 → 拿到 `https://mmbiz.qpic.cn/...` → 替换到正文。
  脚本会把待替换的图片列出来交给用户处理。

## 7. 排版尺寸的通用经验

- **字号以正文为基准**：正文 16px（移动端最佳阅读字号，也是公众号编辑器默认值）是推荐值，
  行高 `1.75`；可选 12 ~ 20px。其余元素按相对偏移推导（正文 16 时：段落/列表/引用 15、
  表格/行内代码 14、代码块 13、H2 19、H3 17、大标题 24），派生字号有 11px 兜底下限。
  要调整就整体调基准，不要单独改某个元素的字号，否则会出现「正文变了、表格没变」的比例错位。
- **配色要成套**：主题色分三层用——`accent` 给装饰（竖条/圆点/分隔线/标题下划条），
  `accent_deep`（同色系压深、白底对比度 ≥ 4.5:1）给**所有标题文字与行内代码文字**，
  `accent_soft` 给底色（引用、行内代码、表头、片尾）。
  把标题设成近黑色会让整篇「看起来没有主题」，而直接用亮主色当文字又会糊 —— 两头都不能踩。
- iPhone 18 Pro 的 CSS 视口是 **402 × 874 pt**（DPR 3×，6.3″，19.5:9），
  正文可用宽度 = 402 − 左右各 20px ≈ **362px**，一行约 22 ~ 23 个汉字。
  算折行效果就用这个宽度，别按 375 或 414 估。
- 段落间距用 `margin-bottom`（1.4em 左右），别用 `<br>` 堆行
- 外层容器不要设固定宽度，微信会自己按屏幕铺满；左右留 `padding: 0 2px` 即可
- 中英文混排加 `letter-spacing: .5px` 会比默认更疏朗透气
- 深色代码块背景配浅色正文可以显著提升"这是一段代码"的辨识度
